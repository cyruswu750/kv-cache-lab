# M2.1 导读（中文）：证据说明了什么，没说明什么

M2.1 不加新功能，只做两件事：

1. **审查 M2 的测量和打分代码**，用"相邻样本不独立"的方法重新分析 M2 已保存的数据，不改动原始文件；
2. **用一个小规模、预先写好假设的诊断实验**，把恢复路径的"慢模式"定位得更具体。

详细数字见 `docs/M2_1_REVIEW.md`，实验计划（含两次事先记录的修正）见 `docs/M2_1_DIAGNOSTIC_PLAN.md`。

## 1. M2 的计时本身没问题

- `synchronize(); t0 … int(argmax); t1` 这个计时边界是对的：所有拷贝都是默认 stream 上的阻塞拷贝，`int()` 会等 GPU 算完。
- 计时区内没有残留的参考 cache 或临时 GPU 张量。M2.1 记录了每个样本的分配器计数，`cudaMalloc` 次数恒为 0。
- 每个样本都检查了层级、恢复长度和准入的 chunk。冻结链（模型 → 预测 → 评估）完整。
- **`full` 的含义需要说清楚**：它是"在已准备好的缓存状态下重算"。前缀其实已在 host 里，只是不去恢复。
  - M2.1 另加了一个**仅作诊断**的 `full_nocache`：完全没有缓存系统，只有 `prefill` 加 `argmax`。
  - 它的 logits 与 `full` 逐位相同，时间差不到 0.4 ms。
  - 它不进入任何历史打分。

## 2. M2 的打分高估了确定性（BUGLOG VAL-005）

慢样本在时间上**成簇**：相邻重复的配对差，自相关高达 0.93。M2 的 bootstrap 却把 40 次重复当成独立样本，置信区间因此偏窄。

M2.1 改用**分块 bootstrap**：按时间顺序，每次整块重抽 1、2、4、8 个相邻重复。只有四种块长结论一致，才算"已确立"。区间含 0 时一律记为 **inconclusive**（不能下结论），**不代表两条路径一样快**。

| | M2 的说法 | M2.1 重新分析后 |
|---|---|---|
| 留出集 18 个决策（看中位数） | 11 个恢复胜，7 个 tie | 9 个恢复胜，9 个 inconclusive（L=1024、S=64 的两个"胜"不再成立） |
| 看均值（期望延迟） | 没报告 | L=512 的 6 个决策里，**重算都确定更快**；模型却选了恢复 |
| 选错代价 | 0 ms | 0 ms 只统计了能判定的决策；按均值，18 个决策的点估计合计 110 ms，其中 92 ms 已在统计上确立 |
| 和简单策略比 | 没比 | 模型的选择**等同于"总是恢复"**，在这份数据上没有带来任何额外的决策收益 |

为什么中位数和均值会给出相反的结论？因为恢复路径的延迟是**双峰**的：快的时候比重算快几毫秒，慢的时候要多约 50 ms。要优化期望延迟就看均值，要看典型延迟就看中位数。两个都报告，不偷换。

另外要说明：有些序列只跨 12–14 秒，而一个慢区间本身就能持续好几秒。这种情况下，即使用分块方法也**无法可靠估计不确定性**，我们如实标注，没有硬给结论。

## 3. 诊断实验：慢模式到底慢在哪里

**做法**：

- 选 3 个代表性用例：(512, 1)、(1024, 64)、(4096, 64)。
- 用 4 条路径 × 3 种计时方式：
  - 原样的 M2 计时；
  - 只打 CUDA event、不做同步的计时；
  - M2 带同步的分阶段计时。
- 在每一轮里随机交替执行；共 9 个独立进程会话，所有原始样本都保留。

**结论**（"已排除"指在这份数据里被对照实验否定）：

| 假设 | 关键对照 | 结论 |
|---|---|---|
| GPU 降频 | 慢样本和快样本的 SM 时钟中位数都是 2370 MHz | 已排除 |
| GPU kernel 本身变慢 | profiler 下，kernel 总时间 9.93 vs 9.92 ms | 已排除 |
| 测量手段导致（同步打点、`nvidia-smi` 监控） | 三种计时方式的慢样本比例相近；关掉监控后慢模式依旧出现 | 不是这些手段导致的 |
| 线程被调度走了 | 线程 CPU 时间 ≈ 墙钟时间，运行队列等待 ≈ 0 | 不是；线程一直在 CPU 上跑 |
| CPU 整体变慢 | SHA-256、纯 Python 循环、普通系统调用的耗时都不变 | 已排除 |
| **只有 CUDA 调用变慢** | 一次 kernel 启动约 10 → 48 µs；一次小的同步 H2D 拷贝约 40 → 90 µs | **成立** |
| 只影响恢复路径 | 在恢复变慢的那些轮里，重算路径"提交 forward"的时间也从 17 ms 涨到 35–38 ms；只是它的 GPU 计算更久，把这部分掩盖了 | 是**共享的状态**，不是恢复路径特有 |
| 显存分配 | 每个样本的 `cudaMalloc` 次数都是 0 | 已排除 |

**一句话总结**：在这台 WSL2 笔记本上，**每次 CUDA 驱动/运行时调用的 CPU 侧开销**会成段地升高 2–5 倍：慢区间中位数 1.4 秒，最长约 10 秒。

- 恢复路径受影响最大，因为它由成千上万次小调用组成：每个 chunk 要做 56 次同步拷贝，后缀 forward 约 1,340 次 kernel 启动。
- 大 N 的重算受 GPU 计算本身限制，提交变慢被掩盖了。

**没有证明的**：究竟是驱动内部、WSL 的 GPU 虚拟化、宿主机的 GPU 调度，还是电源管理导致的。要分辨这些，需要宿主机侧的追踪工具或特权，超出了本里程碑的范围，所以**不声称任何根因**。

另外还观察到一种**不同的**现象：GPU 空闲一段时间后，时钟会降到约 1300 MHz。这时受 GPU 计算限制的重算会变慢（38 → 64 ms），而受启动开销限制的恢复路径基本不受影响。两种效应要分开看。

## 4. 你应该能回答的问题

1. 为什么区间包含 0 时要写 "inconclusive"，不能写 "tie"？
2. 自相关为什么会让普通 bootstrap 的区间变窄？分块 bootstrap 解决了什么，又解决不了什么？
3. L=512 时，中位数说"恢复更快"，均值说"重算更快"。这两个结论各自对应什么样的系统目标？
4. 为什么慢模式同样影响重算路径，它的端到端延迟却看不出来？（提示：比较提交时间和 GPU 执行时间。）
5. 为什么下一步应该优先减少恢复路径上 CUDA 调用的**次数**，而不仅仅是减少搬运的字节数？

## 5. 下一步建议（未开始）

把每个 chunk 的 56 次同步小拷贝，改为一次连续的 H2D 拷贝加设备端摆放，整个恢复只同步一次；然后用 M2.1 的方法（交替执行、分块 bootstrap，中位数与均值同时报告），在**新的**评估集上重新测量。

这一步不改策略、不改格式、不改数值规则，正确性仍以现有的逐位比较为门槛。
