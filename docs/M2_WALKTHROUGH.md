# M2 代码与结果导读（中文）

M2 做了两件事：一是测量现有同步路径的首 token 延迟；二是用校准集拟合一个可解释的成本模型。模型冻结后，再拿到留出集上打分。

运行时策略没有改变，`run()` 仍然总是恢复。实验约定以 `docs/M2_PROTOCOL.md` 为准，结果见 `docs/M2_REVIEW.md` 和 `results/m2/run_20261103T131543/results.md`。

## 1. 计时边界：到底测的是什么

```
torch.cuda.synchronize(); t0
engine.prefill_request(prompt)        # ids 上 GPU → 链式 key → 恢复 → prefill → 写入缓存
int(torch.argmax(logits))             # 首 token 回到 CPU（隐含一次同步）
t1
```

- **指标名称**：tokenized-input first-token latency，即从已分词的输入到调用方拿到第一个 token。它不包含分词和排队，**不是**服务级 TTFT。
- **计入的部分**：查找、逐块校验（CRC、身份）、H2D、`DynamicCache` 组装、后缀 prefill、argmax。
  - 还包括**缓存准入**：现有引擎在选出首 token 之前，先把新的完整 chunk D2H 写进 pinned host，所以这部分必须计入。S = 256 的用例里，它约占 4.5 ms。
- **不计入的部分**：模型加载、状态准备与复位、page cache 处理、正确性检查、参考重放、整份 logits 拷贝、GPU 监控。
- **为什么拆出 `prefill_request()`**：为了复用引擎的真实执行顺序，而不是在测试脚本里另抄一份。`run()` 现在调用它，行为不变（GPU M1 套件 12/12 通过）。
  - `allow_restore=False` 只用于离线测量完整重算。
- **分阶段计时**：`mark()` 只在单独的"插桩样本"里启用。它在每个阶段边界做一次同步，所以各阶段互不重叠，可以相加。插桩样本和正式样本不混在同一个统计量里。
  - 两者的差（同步本身的开销）用校准集上的常数 offset 修正。

## 2. 三条路径与缓存状态（`kvlab/perf_harness.py`）

| 路径 | 状态 | 每个样本都检查 |
|---|---|---|
| full | store A（前缀在 pinned host 里），但不尝试恢复 | L = 0 |
| host | store A：前缀 chunk 在 host slot 中 | L、来源全是 host |
| disk | store B：前缀是磁盘文件，host 里没有前缀 | L、来源全是 disk；计时前 `mincore` 显示 100% 在 page cache 中（**热缓存**） |
| disk_evicted（诊断用，仅 S = 1） | store B：对自己的文件做 `posix_fadvise(DONTNEED)` | 计时前 0% 驻留 |

要点：

- **状态准备**：每个 L 组只用一次不计时的源 prefill 生成 chunk 字节，再通过 M1 的公开接口放进各层。
- **复位**：每个 store 都留有一个空 host slot，所以准入不会触发溢写。准入的 chunk 在计时区之外用 `discard()` 删掉，并在每个样本后断言状态没有漂移。
- **磁盘命中不会变成 host 命中**：disk 命中不回填 host（D15）。
- **为什么不说"NVMe 冷读"**：文件位于 WSL2 的 ext4 虚拟盘上。`fadvise` 只能把页从 Linux page cache 里赶出去，Windows 那一侧可能仍有缓存。真正的冷读需要特权，这一项记为 BLOCKED。

## 3. 采样：如何对付噪声

- 每个 L 组内，每一轮把所有 (S, 路径) 随机打乱后各跑一次。
- winner 用**同一轮内的配对差**（restore − full）来定：中位数加 bootstrap 95% CI。CI 不含 0 才算有胜者，否则记为 **tie**，不参与打分。
- 采样数量：每个用例 5 次预热 + 20 次测量（评估集为 40 次，见修正 A）。插桩样本另做 2 + 20 次。
- `gc.collect()` 每轮只调用一次，计时区内禁用 GC。
- **不报告 p99**：样本量不够。

### 平台漂移（真实测到的，不是假设）

1. **GPU 时钟漂移**：笔记本 GPU 的 SM 时钟在 2385 MHz 和 1335 MHz 之间漂移（原因码含 SW power cap）。GPU 受限的路径因此会变慢约 25%。
   - 没有改任何电源设置，只用只读的 `nvidia-smi -lms 200` 记录时钟，每个样本都能对上当时的时钟。
2. **恢复路径的"慢模式"**：恢复路径的延迟呈双峰分布，慢的一峰大约多出 50 ms。
   - 慢样本在时间上**成簇**：前一个样本慢时，下一个也慢的概率是 84%，而基线是 40%。
   - 评估那次运行的慢样本比例（40%）是校准那次（20%）的两倍。
   - 定位结果：单次 7 MB 拷贝和校验读盘都不会出现尖峰；尖峰出现在"带已有 cache 的前向"以及恢复的端到端样本中。
   - 根因**没有确定**（候选：WSL2 GPU 虚拟化或调度、CPU/GPU 共享功耗），如实记录。

## 4. 成本模型（`kvlab/perf.py`）

```
预测(path) = ingest(N) + restore_path(chunks) + prefill + store(new_chunks) + select + offset_path
```

- 后缀 prefill：`a + b·S + c·S·(L + S/2)`（注意力里 query-key 的对数）。完整 prefill：`a + b·N + c·N²/2`。
  - 不假设 prefill 与 N 成线性：S = 1 时也有约 17 ms 的地板，因为这时瓶颈是 kernel 启动。
  - 校准集里 S 只有 1 和 256 两个值，单独的 S² 项无法辨识，所以合并成注意力对数这一项。
- 拟合：只用校准集各用例的中位数，做非负最小二乘，并按相对误差加权。代码会拒绝任何留出集数据参与拟合。
- 结果：host 每块约 3.6 ms，disk（热缓存）每块约 5.7 ms。
  - 微基准说明，这主要来自"每块 56 次小拷贝 + CRC32 + 组装"，而不是 PCIe 带宽：单次连续拷贝约 12 GB/s，只作参考。
- **冻结流程**：`m2_fit_predict` 写出带 SHA-256 的 `model.json` 和 `predictions.json`，如果评估数据已经存在就拒绝运行。
  - 评估脚本必须读到冻结的预测，并记下它的摘要。
  - 打分脚本会验证整条链：预测早于评估开始，用例与留出集一致，摘要都匹配。

## 5. 怎样读结果

- **winner**：留出集共 18 个决策，其中 11 个可打分，11 个全对，选错代价为 0；另外 7 个是 tie（都在 L ≤ 512）。
  - 注意：模型在整个网格里都预测"恢复更快"，而实测里没有一个用例是"重算明显更快"。所以这只说明模型没有选到明显更慢的路径，**不能**说明它在转折点附近有判别力。
- **延迟误差**：full 的中位误差 3.5%，很准；host 14.3%，disk 5.6%，最大 −67%。
  - 大误差都落在慢模式主导的用例上：模型预测的是"快模式的中位数"，不是均值，也不是尾部。
- **break-even**：在 L = 256…4096 内，没有预测出、也没有可靠测出转折点。
  - 最接近的是 disk、L = 256、S = 1：预测恢复只快 0.5 ms，落在误差范围内。
  - 把 Linux page cache 赶出之后（诊断路径），L = 256 和 512 时与重算打平，L ≥ 1024 时恢复胜出。
  - **不声称任何 break-even 长度**。

## 6. 你应该能回答的问题

1. 为什么缓存准入（D2H）必须算进首 token 延迟？如果只测"恢复 + prefill"，会高估还是低估恢复的收益？
2. 为什么 winner 要用同一轮里的配对差，而不是比较两组的中位数？结合时钟漂移和慢模式成簇来说明。
3. `disk` 路径为什么只能叫"热 page cache 下的应用层磁盘命中"？`disk_evicted` 又排除了什么、没排除什么？
4. 为什么模型在 held-out 上 winner 全对，延迟却会差 67%？这对把模型接入运行时策略意味着什么？
5. 校准集里 S 只有两个值，为什么不能同时拟合 S 和 S² 两项？现在的特征为什么仍然能对 S = 64 做插值？
