## 1. 数据在内存里长什么样

**host 上的一个 chunk**（格式没变）是一块连续的 7,340,032 字节：

```
[layer 0..27][K, V][1, kv_heads=2, C=256, head_dim=128]   bf16，行优先
```

其中每层的 K 或 V 是连续的 131,072 字节。

**baseline 在 GPU 上的目标**是每层一个 K、一个 V 张量，形状 `[1, 2, n·C, 128]`，一共 56 个张量。chunk i 落在这 56 个张量的 `[i·C, (i+1)·C)` 一段。对每个张量来说，这一段是"有步长的"：每个 head 一段 64 KiB，相邻 head 之间隔 n·64 KiB。

所以 baseline 恢复一个 chunk 要做 56 次 `copy_`，每次都是阻塞的 H2D：

- n = 1 时，目标片段恰好连续，每次就是 `cudaMemcpyAsync` + `cudaStreamSynchronize`；
- n > 1 时，目标片段有步长。PyTorch 会先在 GPU 上分配一个连续的临时张量，拷贝进去，再启动一个拷贝 kernel 写进有步长的位置。

结果：恢复 16 个 chunk（L=4096）大约要 900 次同步拷贝、950 次 kernel 启动。这些数字由设计探针实测，见 `results/m3/design_probe/`。

**最后的 cache** 走公开构造函数 `DynamicCache(ddp_cache_data=...)`（决策 D4）。它内部用 `torch.cat` 把 `[0, L)` 再拷贝一次，生成新张量，所以返回的 cache 拥有自己的内存。这一步固定是 56 个 kernel，两种后端都一样。

## 2. batched 后端怎么搬

两块 GPU 缓冲区，都是"每次恢复各分配一次"，用完就释放：

- **X（chunk-major 暂存）**：形状 `[g, layer, K/V, 1, head, C, head_dim]`，最多 g = min(n, G) 个 chunk。默认 G = 4，最多 28 MiB。
- **Y（layer-major 目标）**：形状 `[layer, K/V, 1, head, n·C, head_dim]`，一个张量装下全部 n 个 chunk。

流程：

1. **每个 chunk 一次连续的 H2D**：把整块 7 MB slot 一次拷进 X 的下一行。源和目标都连续，所以只有 1 次 `cudaMemcpyAsync` 和 1 次同步，没有 kernel。
2. **每组（≤ G 个 chunk）一次放置**：把 X 视为 `[layer, K/V, 1, head, g, C, head_dim]`（permute 只改视图，不拷贝），把 Y 中这一组的目标段视为同样形状（unflatten 也只改视图），然后一次 `copy_` 完成整组。这是 1 个 device 操作，不是每个 chunk 56 次 D2D。
3. **最后一组**（可能不满 G）在构建 cache 前补放。
4. 用 Y 中 `[0, L)` 的 56 个视图调用公开构造函数（与 baseline 相同），得到拥有自己内存的 cache。

估算的调用次数（host 或 disk，G = 4）：

| n | baseline memcpy / 同步 / kernel | batched memcpy / 同步 / kernel |
|---|---|---|
| 1 | 56 / 56 / 56 | 2 / 1 / 56 |
| 16 | 896 / 896 / 952 | 16 / 16 / 60 |

两种后端都包含构造函数的 56 个 kernel。实测数见 `M3_REVIEW.md`。

为什么不选"每个 chunk 一次有步长的 `copy_`"（选项 a）？

- 两者的传输次数相同。
- 但 a 要 n 次放置 kernel，而且依赖 PyTorch 内部的隐式临时张量。
- b 的暂存区是显式的、有上界的，放置次数是 ⌈n/G⌉。

两者的差别只有几次 kernel 启动，我们不把它当作单独的收益来报告。

## 3. 所有权与生命周期（谁拥有哪块内存、什么时候能复用）

- **host slot**：在 `with host.lease(key)` 期间被"钉住"，不会被驱逐。
  - H2D 是阻塞拷贝：`copy_` 返回时传输已经结束。
  - lease 在传输完成之后才释放。
- **staging slot**（只有一个，用于磁盘 chunk）：流程是 `read_into`（CPU 写入）→ 阻塞 H2D → 释放。
  - 下一个磁盘 chunk 的读入一定在上一次传输完成之后才开始。
  - 任何时刻最多只有一次传输在读 staging。
  - 我们**没有**"连续排队多个磁盘传输、最后才同步一次"。
- **X**：只有 H2D memcpy 写它，只有放置 copy 读它，全部在当前 stream 上。
  - 下一组的 memcpy 在同一 stream 上排在上一组放置之后。
  - 而且是阻塞的，所以不会覆盖还在被读的数据。
  - 函数返回时释放。PyTorch 的缓存分配器只会把这块内存交给同一 stream 上更晚的工作，这些工作都排在已入队的读之后。
- **Y**：被构造函数的拷贝 kernel 读取，返回时释放，规则同上。
- **返回的 cache**：张量是构造函数新建的，正好 L 个 token。没有视图把 X 或 Y 的大块内存"拖住"。测试断言了每层 storage 的大小等于它的 L-token 载荷。之后的请求、缓冲区复用、host slot 被改写，都改变不了它。
- **出错时**：拷贝中的 CUDA 或程序错误照常抛出，不会被当作 cache miss。lease 和 staging 由 `with` 在 `finally` 中释放，X/Y 随引用消失，不会构建 cache。命中计数只在拷贝完成后才加 1；变异检查发现原来的测试没有覆盖这一点，现已补上。
- **部分前缀**：遇到第一个缺失、损坏或不兼容的 chunk 时：
  - 先放置当前组里已经验证过的部分；
  - 再只用 `[0, L)` 构建 cache；
  - Y 中没写过的部分永远不会暴露。

## 4. 同步策略：为什么不用 non_blocking

所有拷贝都是 `non_blocking=False`。PyTorch 的阻塞 H2D 等于 `cudaMemcpyAsync` 加 `cudaStreamSynchronize`（设计探针实测）。

只写 `non_blocking=True` 并不能保证安全：

- PyTorch 只会为它**自己的**缓存式 pinned 分配器记录事件。
- 我们的 slab 是用 `cudaHostRegister` 注册的，不在其中。
- 如果改成异步，lease 和 staging 的释放就必须由我们自己等到传输完成。

M3 选择每个 chunk 阻塞一次：同步次数从 56·n 降到 n，正确性推理也最简单。

GPU 测试 `test_every_chunk_transfer_is_one_synchronizing_copy` 用 PyTorch 的同步调试模式守住这一点：

- 6 个 chunk 时，baseline 应有 336 次同步，batched 应有 6 次；
- 把拷贝改成 `non_blocking` 的变异体会被这个测试杀死。

## 6. 性能结果（5 个独立进程会话，5,400 个样本，0 个排除，一个都没过滤）

d = batched − baseline，在同一次重复内配对（单位 ms）。区间来自分层块 bootstrap：只在连续的块内重抽，不把两段不相邻的时间拼在一起。

**端到端首 token 延迟**（M2 的计时边界，包含恢复、暂存、放置、构造函数拷贝、后缀 prefill、准入）：

| 用例 | 层 | baseline 中位数 → batched | 配对中位数 d | 配对均值 d | 判定 |
|---|---|---|---|---|---|
| (256, 32) 1 chunk | host | 23.9 → 22.5 | −2.0 | −6.4 | 更快 |
| (1024, 1) 4 | host | 33.3 → 21.3 | −12.3 | −18.1 | **inconclusive（R3：时长不足）** |
| (1536, 128) 6 | host | 43.7 → 25.9 | −17.9 | −28.7 | 更快 |
| (3072, 256) 12，含准入 | host | 78.7 → 41.7 | −37.0 | −59.8 | 更快 |
| (4096, 64) 16 | host | 86.2 → 37.6 | −48.5 | −80.8 | 更快 |
| (4096, 64) 16 | disk | 117.7 → 65.0 | −52.8 | −82.5 | 更快 |

完整表格（包括所有 disk 行和各块长的区间）见 `M3_REVIEW.md` §6。

**三种"加速比"是不同的量，不能混用：**

- 中位数之比 = median(baseline) / median(batched)，例如 4096 host 为 2.29；
- 均值之比 = mean(baseline) / mean(batched)，同一用例为 2.48；
- 配对比值的中位数 = 每次重复的 baseline/batched 取中位数，同一用例为 2.32。

**恢复阶段**（单独的同步打点样本，诊断用）：host 在 16 个 chunk 时从 62.6 ms 降到 12.1 ms；disk 从 90.8 ms 降到 39.4 ms。

disk 剩下的部分主要是校验后的文件读取和 CRC，每个 chunk 约 1.7 ms（来自页缓存），两种后端一样。

**实测调用次数**（torch.profiler，单次 `restore()`）：

| chunk 数 | baseline memcpy / 同步 / kernel | batched |
|---|---|---|
| 1 | 56 / 56 / 56 | 2 / 1 / 56 |
| 16 | 896 / 896 / 952 | 16 / 16 / 60 |

这与设计时的估算完全一致。整次请求的 kernel 启动在 16 个 chunk 时从 2,192 降到 1,300，剩下的主要是后缀 forward。

**显存**：

- batched 每次恢复多用 min(n, 4) 个 chunk 的暂存，最多 29.4 MB。
- 恢复结束后两者只保留 cache 本身。
- L=3072 时 `memory_allocated` 多出约 2 个 chunk。这是 PyTorch 缓存分配器对 1.5 MiB 张量的块取整，requested 字节正好等于载荷，两种后端一样，不是视图拖住了暂存区。
- 没有新的 host 内存。

## 7. 结论该怎么读

- **改善很大、方向一致**：凡是规则能判定的地方都是 batched 更快，5 个会话方向全部一致，没有任何回归。
- **但预先登记的采纳规则没有完全满足。**
  - (1024, 1) 的方向在所有块长和所有会话中都一致，但它的测量总时长 73 s，不到最长慢区间（8.2 s）的 10 倍，所以按 R3 记为 inconclusive。
  - 这条规则是事先定好的，我们照实报告，不事后改规则。
- **默认后端仍是 `baseline`**，等你审阅。切换只需要一个参数。
  - （*更正后补充*：经过 VAL-006 校验的重新分析，结论仍是 `supports_adoption = false`，唯一原因是 (1024, 1) 按 R3 为 inconclusive。）
- **慢模式还在**：两种后端的慢样本比例相近（33–42%），均值仍明显高于中位数。
  - batched 减少的是恢复路径上的调用次数，并没有消除慢模式。
  - 现在剩下的调用主要来自后缀 forward（每次请求约 1,150–1,350 次 kernel 启动）、准入时的 56 次 D2H，以及构造函数的 56 个 kernel。
  - 慢模式只是"与主机侧 CUDA 调用开销升高相关"，根因仍未确定。
- **M2.1 的统计方向是条件性的**，例如"L=512 时按均值重算更快"。那只针对当时的样本和 baseline 后端，不能直接套用到 batched。

## 10. 更正：分析前的证据校验（VAL-006，M3 之后补充）

**问题。** 旧的分析脚本从已加载的数据推断实验应包含什么：

- 会话 = 目录里有的 `session_s*.json`；
- 用例 = 已加载样本里出现过的 (L, S)。

这带来了三个后果：

- 判定规则只遍历这些用例，缺失的必需用例既不会失败，也不会被报告；
- 正确性门槛 (1) 直接相信存储的汇总标志，并且对空集合 `all([])` 也算通过；
- 不完整的配对会被悄悄丢掉。

**现在的做法**（`kvlab/m3_validate.py`，在任何统计之前运行，不需要 CUDA 或模型权重）：

- **显式规格 `m3_eval_20261103T173632`**，来自冻结的协议和记录下来的命令：
  - 5 个会话及其种子、5 个用例、每用例 2 个块；
  - 每块 2 次 warmup + 12 次测量重复，每次重复 9 个 path/backend/mode 样本；
  - G = 4、git HEAD、执行测量的源文件。
- **测量样本**：每个 (block, rep, path, backend, mode) 身份必须恰好出现一次（共 5,400 个），并通过 M2/M3 有效性规则，否则配对不完整。
- **warmup 证据**（补充修复）：warmup 不参与任何统计，但它是冻结流程的证据，所以同样要完整。
  - **块 warmup** 按身份检查：900 个，每个恰好一次。
  - **进程 warmup** 按冻结的运行脚本检查：在最小和最大用例 (256, 32)、(4096, 64) 上，每个组合各两次，每个会话 36 条，共 180 条。
    - 历史记录没有重复编号，所以按 (用例, 组合) 的出现次数核对，不虚构、不改写任何历史字段。
    - 它们必须标记为 warmup、不带 block/rep，并出现在第一个块样本之前。
  - 缺失、重复、替换（总行数不变的也算）、多余、标志或 stage 错误的 warmup 都判为无效。
- **正确性和 A/B 检查**：
  - 每个用例恰好一条记录，详细字段必须齐全；
  - 是否通过由详细字段重新计算，与规格给出的数量比较：50 个 strict 检查（会话 × 用例 × 后端）和 50 个 A/B 检查（会话 × 用例 × tier）；
  - 存储的汇总标志只用来比对，不被信任；
  - A/B 记录还必须表明两次请求都从该 tier 恢复了整个前缀。
- **判定**：`decide()` 遍历规格里的用例列表；分析中缺少的规格用例会阻止采纳。

**三种状态，三个退出码：**

- `valid`：退出码 0，写出分析。结论仍可能是 inconclusive，这是有效结果，不是无效证据。
- `invalid`：退出码 3，不写分析，`supports_adoption` 为 false。
- `correctness_failed`：退出码 4，同样不写分析，不采纳。

**不变的部分**：R1–R3、自助法、种子、所有数值代码、测量代码、冻结协议和默认后端 `baseline`。

**证据**：

- `results/m3/reanalysis_val006_20261103T200427/`（首次修复）；
- `results/m3/reanalysis_val006_warmups_20261103T202825/`（warmup 补充修复）。

两处都包含修复前和修复后的复现日志、与历史分析的逐值比较，以及保留性检查。
